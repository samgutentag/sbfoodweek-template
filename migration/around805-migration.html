around805.com Food Week Migration

Runbook, drafted 2026-09-23. Redirects first, code later.

Goal: every food week map lives at around805.com/<food>week<year>. Phase 1 makes those URLs work today by redirecting them to the existing domains. Phase 2, run per event once its code is hosted under around805.com, flips the direction so the old domains redirect in. Nothing in Phase 1 touches the old sites.

around805.com is on Cloudflare, proxied, and currently answers every path with a 302 to https://gutentag.world/ (path dropped, query string kept). That catch-all is the one thing Phase 1 has to work around.

Phase 1: around805.com paths redirect to the old domains

About 20 minutes, all in the Cloudflare dashboard. Uses one Bulk Redirect list: migration/bulk-redirects-phase1.csv.

  1. Find the gutentag.world catch-all. In the around805.com zone, check Rules > Redirect Rules, then Page Rules, then account-level Bulk Redirects. Note which one it is.
  2. Narrow it so it skips the week paths. Single Redirects run before Bulk Redirects, so an untouched catch-all swallows everything. If it is a Redirect Rule, set its expression to: 
    not (starts_with(http.request.uri.path, "/burgerweek")
  or starts_with(http.request.uri.path, "/coffeeweek")
  or starts_with(http.request.uri.path, "/sandwichweek"))
    If it is a Page Rule, recreate it as a Redirect Rule with that expression and delete the Page Rule. Leave /burritoweek under the catch-all until burrito goes live.
  3. Create the list. Account home > Bulk Redirects > Create Bulk Redirect List. Name it around805_phase1, upload bulk-redirects-phase1.csv.
  4. Create the rule. Bulk Redirects > Create Bulk Redirect Rule, pick around805_phase1, deploy.
  5. Verify. migration/verify-redirects.sh phase1. Every line should say ok. Before setup, the around805 checks fail by landing on gutentag.world, which is expected.

Every entry is a 302 on purpose. These redirects get reversed in Phase 2, and browsers cache a 301 hard enough that people would keep bouncing to the old domain after the flip. The year aliases stay 302 forever, since they move every year.

One-time: make around805.com a host

Needed before Burrito Week launches and before any Phase 2 cutover. About 30 minutes. The site itself is the single repo described in docs/superpowers/specs/2026-09-23-around805-single-repo-design.md, deployed to Cloudflare from GitHub Actions.

  1. Test the deployed site on its Cloudflare preview URL first. Check every event path.
  2. Attach around805.com as the project's custom domain (plus www). Cloudflare replaces the zone's records and keeps them proxied, and Bulk Redirects only fire on proxied traffic.
  3. Retire the gutentag.world catch-all. The site root becomes the event landing page. The latest-year aliases (/burgerweek and the rest) move into the repo's generated _redirects, so delete those three lines from around805_phase1 at the same time.

Phase 2: old domain redirects to around805.com (per event)

About 30 minutes per event. Do one event, verify, then the next. Burger as the example.

  1. Confirm events/burgerweek2026/ is imported and renders on the preview URL. You can't test the live path yet, because the Phase 1 entry still intercepts it.
  2. Delete the around805.com/burgerweek2026 entry from around805_phase1. Keep the /burgerweek alias. Load the live path and confirm the map renders.
  3. Add the burger line from bulk-redirects-phase2.csv to a second list, around805_phase2, with its own Bulk Redirect Rule. It does nothing yet, because the domain is still grey-clouded.
  4. Check the sbburgerweekmap.com zone's Edge Certificate shows Active (SSL/TLS > Edge Certificates), then flip its apex A records and the www CNAME to proxied. The redirect takes effect as soon as traffic hits Cloudflare. The GitHub origin stays in place but is never reached.
  5. Verify with migration/verify-redirects.sh phase2 burger. After a clean week, change that entry to 301. Later, clear the custom domain on the old repo and delete its CNAME file.
Never run both directions for one event. Step 2 (remove the Phase 1 entry) always comes before step 4 (proxy the old domain). If both are active, around805.com/burgerweek2026 and sbburgerweekmap.com bounce off each other. The verify script catches that as a loop.

Code migration

Settled: one repo for every event, with URL-driven event selection and past years kept forever. The design, the code changes, and the migration order are in docs/superpowers/specs/2026-09-23-around805-single-repo-design.md. Checklists saved in browsers on the old domains don't carry over to around805.com, since it's a different origin. That's fine for archived events.
