around805.com Food Week Migration

Runbook. Drafted 2026-09-23, status updated 2026-09-24.

Goal: every food week map lives at around805.com/<food>week<year>, served from one repo, with past years kept forever and /<food>week always loading the newest year. Phase 1 makes the new URLs work now by redirecting to the old domains. The code migration builds the single-repo site. Phase 2 then flips each old domain to redirect in.

Phase 1: around805.com paths redirect to the old domains

About 10 minutes, all in the Cloudflare dashboard. Uses one Bulk Redirect list: migration/bulk-redirects-phase1.csv.

  1. Find the gutentag.world catch-all. Done: it's a Redirect Rule in the around805.com zone.
  2. Narrow it so it skips the week paths. Done 2026-09-24 for the burrito launch. Redirect rules run before Bulk Redirects and before Workers, so the catch-all has to skip these paths or it swallows them. For reference, the expression is: 
    not (starts_with(http.request.uri.path, "/burgerweek")
  or starts_with(http.request.uri.path, "/coffeeweek")
  or starts_with(http.request.uri.path, "/sandwichweek")
  or starts_with(http.request.uri.path, "/burritoweek"))
  3. Create the list. Account home > Bulk Redirects > Create Bulk Redirect List. Name it around805_phase1, upload bulk-redirects-phase1.csv.
  4. Create the rule. Bulk Redirects > Create Bulk Redirect Rule, pick around805_phase1, deploy.
  5. Verify. migration/verify-redirects.sh phase1. Every line should say ok. Any path still broken takes about 20 seconds to time out, so a slow run means something failed.

Every event entry is a 302 on purpose. Phase 2 reverses these redirects, and browsers cache a 301 hard enough that people would keep bouncing to the old domain after the flip. The year aliases stay 302 forever, since they move every year. Only www gets a 301, because it never changes.

Make around805.com a host

After the code migration session. About 30 minutes. The site is the single repo described in the spec, deployed to Cloudflare from GitHub Actions.

  1. Test the deployed site on its Cloudflare preview URL first. Check every event path and every /<food>week alias.
  2. Delete the interim Worker around805-burritoweek2026 and its route, then attach around805.com (plus www) as the new project's custom domain, back to back. Records stay proxied, so Bulk Redirects keep firing.
  3. Retire the gutentag.world catch-all. The site root becomes the event landing page. The build's generated _redirects takes over the latest-year aliases, so delete the four alias lines (/burgerweek, /coffeeweek, /sandwichweek, /burritoweek) from around805_phase1 at the same time. Keep the www line.

Phase 2: old domain redirects to around805.com (per event)

About 30 minutes per event. Do one event, verify, then the next. Burger as the example. Burrito has no old domain, so it skips this phase.

  1. Confirm events/burgerweek2026/ is imported and renders on the preview URL. You can't test the live path yet, because the Phase 1 entry still intercepts it.
  2. Delete the around805.com/burgerweek2026 entry from around805_phase1. Load the live path and confirm the map renders.
  3. Add the burger line from bulk-redirects-phase2.csv to a second list, around805_phase2, with its own Bulk Redirect Rule. It does nothing yet, because the domain is still grey-clouded.
  4. Check the sbburgerweekmap.com zone's Edge Certificate shows Active (SSL/TLS > Edge Certificates), then flip its apex A records and the www CNAME to proxied. The redirect takes effect as soon as traffic hits Cloudflare. The GitHub origin stays in place but is never reached.
  5. Verify with migration/verify-redirects.sh phase2 burger. After a clean week, change that entry to 301. Later, clear the custom domain on the old repo and delete its CNAME file.
Never run both directions for one event. Step 2 (remove the Phase 1 entry) always comes before step 4 (proxy the old domain). If both are active, around805.com/burgerweek2026 and sbburgerweekmap.com bounce off each other. The verify script catches that as a loop.

Code migration

Settled: one repo for every event, with URL-driven event selection, /<food>week redirecting to the newest non-draft year, and past years kept forever. The design, the code changes, and the migration order are in docs/superpowers/specs/2026-09-23-around805-single-repo-design.md. Checklists saved in browsers on the old domains don't carry over to around805.com, since it's a different origin. That's fine for archived events.
